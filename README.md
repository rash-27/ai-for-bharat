# Project Darpan - Unified Business Identity & Activity Graph

An overlay architecture designed to solve the problem of fragmented, siloed business identity data across government departments (Labour, BESCOM, KSPCB). Darpan actively monitors legacy operational databases, probabilistically matches records using Machine Learning (XGBoost), and constructs a **Unified Business ID (UBID)** within a Graph Database—all without altering a single byte of source data.

## Internal Components & Architecture

This project is built on a distributed, event-driven architecture to ensure high throughput, fault tolerance, and zero interference with existing state systems.

### 1. The Data Silos (Simulated)
* **Component:** PostgreSQL (Supabase/Local)
* **Role:** Acts as the legacy operational databases. Contains three distinct tables (`labour`, `bescom`, `kspcb`) representing isolated government departments. 

### 2. Ingestion Layer (Change Data Capture)
* **Component:** `backend/cdc_worker.py` -> Apache Kafka
* **Role:** Continuously polls the legacy databases for new or updated records (using `updated_at` timestamps). When a change is detected, it pushes a standardized JSON event to the `raw-business-events` Kafka topic.

### 3. The Resolution Engine (ML Inference)
* **Component:** `backend/resolution_engine.py` & `backend/train_model.py` (XGBoost)
* **Role:** The brain of the operation. It acts as a Kafka consumer, picking up new business events. It extracts string similarity features (Jaro-Winkler, Levenshtein) and uses a pre-trained XGBoost model to evaluate the probability that the new record matches an existing business. 
    * **Score > 0.90:** Auto-Links the records.
    * **Score 0.70 - 0.89:** Flags as an Ambiguous Match for human review. *(Human resolutions are logged to `training_logs.csv` for active learning)*.
    * **Score < 0.70:** Rejects the match (isolated record).

### 4. Graph State Management
* **Component:** Neo4j
* **Role:** Stores the structural identity of businesses. Records are nodes. Linkages are edges (`SAME_AS` or `PENDING_REVIEW`). A "UBID" is dynamically generated by querying connected components in this graph.

### 5. High-Speed Search Index
* **Component:** Algolia
* **Role:** Neo4j is slow at fuzzy text search. As the Resolution Engine finalizes UBIDs, it dual-writes a flattened version of the record to Algolia. This powers the sub-second UI search bar without bottlenecking the graph database.

### 6. API Backend
* **Component:** `backend/main.py` (FastAPI)
* **Role:** Acts as the bridge between the React frontend and the databases. It safely queries Algolia for searches, traverses Neo4j to generate the Active/Dormant Intelligence Maps, and handles the `POST` requests when a human reviewer approves a pending merge.

### 7. Frontend UI
* **Component:** React + Vite (`frontend/`)
* **Role:** The Reviewer & Intelligence Dashboard. Provides the side-by-side "diff" viewer for human-in-the-loop resolutions and visualizes the Kafka event timeline to justify a business's "Active" or "Dormant" status.

## Instructions to Run (Local Sandbox)

### Prerequisites
* Docker & Docker Compose
* Python 3.9+
* Node.js & npm
* Supabase Account (for PostgreSQL)
* Algolia Account (for free Search Index)
* Neo4j AuraDB Account (or local Neo4j Desktop instance)

### Step 1: Environment Variables
Create a `.env` file in the `backend/` directory with the following keys:
```env
# Database (PostgreSQL)
SUPABASE_DB_URL=postgresql://postgres:[PASSWORD]@[HOST]:6543/postgres

# Kafka
KAFKA_BOOTSTRAP_SERVERS=localhost:9092

# Neo4j
NEO4J_URI=bolt://localhost:7687
NEO4J_USERNAME=neo4j
NEO4J_PASSWORD=password

# Algolia
ALGOLIA_APP_ID=your_app_id
ALGOLIA_SEARCH_API_KEY=your_search_key
ALGOLIA_WRITE_API_KEY=your_write_key
```

### Step 2: Boot Infrastructure
Start the local Zookeeper and Kafka broker using Docker.
```bash
docker-compose up -d
```
*(Wait ~30 seconds for Kafka to fully initialize).*

### Step 3: Setup the Backend & Data Seed
Install the Python dependencies, generate the synthetic data, and train the XGBoost model.
```bash
cd backend
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt

# 1. Seed the PostgreSQL database with mock Labour, BESCOM, and KSPCB records
python seed_data.py

# 2. Train the ML model on the seeded dataset (Generates model.pkl)
python train_model.py
cd ..
```

### Step 4: Setup the Frontend
Install the React dependencies.
```bash
cd frontend
npm install
cd ..
```

### Step 5: Start the Overlay Architecture
You can run the provided shell script from the root directory to boot the FastAPI server, the React frontend, the CDC Worker, the data populator (`populate_records.py`), and the Resolution Engine simultaneously.

```bash
chmod +x start_all.sh
./start_all.sh
```
* **Frontend Dashboard (Darpan | AI for Bharat):** `http://localhost:5173`
* **Neo4j Visualizer:** `http://localhost:7474` (If running locally, else use your AuraDB console)
